# Эксплуатация Remnawave VPS Bootstrap

Скрипт первоначальной настройки нового VPS с существующей панелью Remnawave. Проверен на реальном Ubuntu 24.04 VPS: установка, DoT/BBR, HTTPS, подключение к панели, работа форка и внешний VLESS Reality Vision. Результаты и границы проверки — в [VERIFICATION.md](VERIFICATION.md). [Главная инструкция](../README.md).

## Запуск

Скопируйте **всю папку репозитория** на VPS, например в `/root/remnawave-vps-bootstrap`. Рабочие файлы: bootstrap.sh, panel_setup.py, ops.py, host_options.sh, monitor.py, rollback.sh, external-test.sh. Запустите:

```bash
sudo bash /root/remnawave-vps-bootstrap/bootstrap.sh
```

Введите домен ноды, исходящий публичный IPv4 панели, HTTPS URL панели, уникальное имя ноды/профиля и API-токен. Имя: 3–20 букв/цифр, подчёркивание или дефис.

Если панель открывается по секретной ссылке с одним параметром вида `?name=value`, вставьте **всю ссылку**, включая параметр. Поддерживаются корень сайта и `/auth/login`. Скрипт передаёт параметр как access-cookie вместе с API-токеном. В state.json сохраняется только HTTPS origin, cookie/секретный параметр на диск не записываются. Эту ссылку нужно вводить заново при каждом запуске, включая тестовые режимы; при откате она запрашивается отдельно.

Ошибка `Remote end closed connection without response` возможна, если cookie-защита Caddy разрывает запрос без параметра доступа. Для проверки после обновления файлов выполните `sudo bash /root/remnawave-vps-bootstrap/bootstrap.sh --check-api`: режим проверяет четыре API endpoint и не запускает apt, настройку firewall или создание ноды. GET-запросы повторяются до трёх раз при сетевом сбое; POST не повторяются автоматически, чтобы не создавать дубликаты. Диагностика показывает endpoint и origin без токена/cookie. Если сбой остаётся при корректной полной ссылке, проверьте reverse-proxy и доступность API из сети VPS.

Домен должен иметь A-запись на IPv4 VPS, без CDN/Cloudflare proxy. Этот вариант рассчитан на IPv4 и требует отсутствия AAAA. TCP 80, 443, 2222 должны быть свободны. В firewall провайдера разрешите SSH и TCP 80/443; TCP 2222 — только с фактического исходящего IPv4 панели. Скрипт настраивает UFW, но не firewall провайдера.

API панели должен быть доступен с VPS через HTTPS с доверенным сертификатом. Tinyauth/Cloudflare Access могут блокировать API даже при правильном токене: заранее настройте доступ для VPS.

Права токена: читать ноды, профили, хосты и Internal Squads, получать ключи, создавать профиль/ноду/хост. Для выбора Squad нужны права изменения Internal Squads. Для тестового пользователя нужны создание/удаление пользователей и Internal Squads; для отката — удаление созданных нод/хостов/профилей. API-токен на диск не сохраняется.

URL панели и API-токен вводятся видимо, одной строкой. Пробелы и невидимые символы по краям токена, необязательный префикс `Bearer ` и парные кавычки вокруг JWT удаляются. Одиночный завершающий обратный слеш удаляется только если оставшаяся строка имеет три непустые части JWT/base64url; именно такой лишний символ был причиной HTTP 401 на тестовом VPS. Подпись и действительность проверяет API панели. Для остальных токенов допускаются печатные ASCII-символы, включая `+`, `/`, `=`. Неполный JWT, пустой токен, пробелы внутри и управляющие символы вызывают повторный запрос токена. Проверка URL выполняется отдельно и не сообщает об ошибке ссылки при повреждённом токене.

При HTTP 401 обновите panel_setup.py и снова выполните `sudo bash bootstrap.sh --check-api`. Диагностика выводит только структуру JWT, категорию роли и признак срока действия; подпись при таком разборе не проверяется. Сам токен, UUID/остальные claims и cookie не выводятся. Для ответа 401 показываются ограниченные данные ошибки с маскированием введённых секретов и тип challenge Basic/Bearer. JSON-ответ может указывать на API, HTML/Basic — на внешнюю защиту; это признаки, а не доказательство источника отказа.

Если корректный бессрочный токен API с полными правами получает 401, сначала заново скопируйте его полное значение в панели нужного домена и проверьте через --check-api. Если отказ сохраняется, сравните на сервере панели авторизованный GET к локальному backend и через reverse-proxy: локальный успех при внешнем 401 указывает на proxy/передачу Authorization; локальный 401 — на проверку токена в backend. Токен и секретную ссылку в диагностические сообщения не вставляйте. Это отдельная диагностика; менять конфигурацию сервера или отключать защиту скрипт не пытается.

## Установка и закрепление версий

Скрипт обновляет apt-пакеты, проверяет Docker и плагин Compose, устанавливает отсутствующие компоненты, проверяет DNS/API/порты и сохраняет резервную копию. Чужие файлы, контейнеры и объекты панели не перезаписываются.

Используется [remnawave-reverse-proxy](https://github.com/eGamesAPI/remnawave-reverse-proxy/tree/7ba662b17ed57d2ba75a57e3c8bada671df65b9f) на commit 7ba662b17ed57d2ba75a57e3c8bada671df65b9f. Адаптер загружает определения до проверенного маркера входа в меню и вызывает его модули install_node_caddy и node_core. Обновление upstream требует пересмотра адаптера.

Образы ноды и Caddy закрепляются по Docker RepoDigest. Первый запуск разрешает ссылки upstream в digest; последующие используют сохранённые digest. Upstream использует remnawave/node:latest, поэтому первый выбор зависит от доступного образа и может различаться на разных новых VPS. Совместимость проверяется при запуске; закрепление не означает заранее проведённое испытание выбранной версии.

UFW сохраняет SSH-порты, включая порт текущей сессии. TCP 80/443 разрешены, 2222 — только с IP панели. Правила ограничения 2222 ставятся первыми.

Создаются индивидуальные Reality-ключи и shortId. VLESS TCP Reality слушает 0.0.0.0:443; selfsteal направляет чужой TLS в /dev/shm/nginx.sock, где Caddy обслуживает сайт с настоящим сертификатом. Caddy не занимает TCP 443, HTTP-01 использует 80. xver: 1 согласован с proxy_protocol.

Создаются Config Profile, Node и Host. clients: [] намеренно пустой: пользователи добавляются панелью. Для каждой новой ноды создаётся уникальный тег `VLESS_REALITY_<имя ноды>`: теги глобально уникальны в Remnawave. При повторном запуске после 409 старый локальный тег `VLESS_REALITY` заменяется только если профиль ещё не зарегистрирован; ключи и shortId сохраняются. У зарегистрированных профилей теги не переименовываются. Затем предлагается выбор существующего Internal Squad по номеру или пропуск через Enter. Добавляется только inbound текущей ноды, существующие inbound’ы сохраняются. При пропуске добавьте inbound вручную.

Ядро заменяется через модуль upstream на [Jolymmiles/Xray-core v26.9.5-0936](https://github.com/Jolymmiles/Xray-core/releases/tag/v26.9.5-0936). Проверяются фактический процесс/путь/версия ядра, SHA256 бинарника и процесса, Xray-конфиг, состояние ноды в панели и HTTPS selfsteal.

Открыть меню установленного reverse-proxy:

```bash
sudo bash /var/lib/remna-bootstrap/reverse-proxy/install_remnawave.sh
```

## Обязательный checksum форка

Архив сначала проверяется по SHA2-256 из .dgst. Отсутствующий, некорректный или несовпадающий checksum **останавливает установку**. После проверки upstream-модуль получает локальный проверенный бинарник и применяет его обычным способом.

Архив, .dgst, бинарник и сведения о релизе сохраняются в /var/lib/remna-bootstrap/verified-core/. Проверка обнаруживает повреждение/несовпадение; checksum и архив получаются из одного GitHub-релиза, это не независимая цифровая подпись автора.

Если версия Remnawave выбирает другое ядро через профиль, скрипт обнаруживает переопределение и восстанавливает предыдущее локальное состояние ядра. Совместимость любых будущих версий панели/ноды не гарантируется.

## Резервные копии и откат

Копии хранятся в /var/lib/remna-bootstrap/backups/, пути выводятся при установке. Две точки: исходное состояние перед изменением стека/опций и состояние перед заменой ядра.

Копируются Compose, Caddyfile, существующий бинарник форка и его state, HTML, UFW, DNS/BBR/monitor-конфигурации, локальное состояние установки и ключи. Сохраняются runtime BBR/qdisc и состояние сервисов, записи панели/групп и исходные UUID. Копии имеют checksum и закрыты от других пользователей.

Если установка форка или его итоговая проверка падает, EXIT-обработчик автоматически восстанавливает локальные файлы/бинарник из точки перед заменой ядра и пересоздаёт стек. Если восстановление само не удалось, ошибка явно выводится.

Полный откат к выбранной точке:

```bash
sudo bash /root/remnawave-vps-bootstrap/rollback.sh /var/lib/remna-bootstrap/backups/ИМЯ_КОПИИ
```

Запрашиваются API-токен и слово ROLLBACK. Сначала проверяются пути/checksum, затем:

- удаляются только записанные новые объекты панели, которых не было в выбранной точке;
- убирается только добавленный этим запуском inbound из Squad, остальные текущие inbound’ы сохраняются;
- удаление отказывается выполняться, если профиль/inbound уже используют посторонние ноды, хосты или группы;
- восстанавливаются файлы, runtime sysctl, firewall и состояние Unbound/monitor;
- возвращается предыдущий стек либо останавливается новый, если его прежде не было.

Это не транзакция с apt: обновлённые пакеты, Docker-образы, ACME-сертификаты и volumes остаются. Если прежнего стека не было, контейнеры остаются остановленными. Полный volume с сертификатами не копируется. Исключите одновременное редактирование этих объектов в панели: API обновления Squad заменяет весь список inbound’ов.

При потере ответа на POST объект может создаться без сохранённого UUID. Скрипт останавливается на конфликте и не принимает неизвестный объект за свой. Проверьте его в панели и восстановите UUID либо удалите только подтверждённый неиспользуемый объект. Неизвестные объекты автоматически не удаляются.

Повторный запуск с теми же параметрами использует сохранённые UUID, ключи и digest. Изменение параметров и исчезновение ранее созданных объектов приводят к остановке. Не удаляйте state.json на живой ноде для обхода проверки.

## Опциональные DNS и BBR

В начале установки предлагаются:

- **BBR/fq**, по умолчанию выключен: проверка поддержки ядром, сохранение исходных значений, применение только /etc/sysctl.d/90-remna-bootstrap.conf.
- **Unbound + DNS-over-TLS**, по умолчанию выключен: локальный resolver на 127.0.0.1:5335, кеш, Quad9 и Cloudflare через TLS с проверкой сертификатов. До переключения systemd-resolved выполняется реальный DNS-запрос.

Порт 853 к upstream должен быть доступен. Если все DoT upstream недоступны, настройка останавливается. В resolved прописаны резервные адреса, но они не гарантируют переключение при любой ошибке Unbound. При ошибке выводится путь исходной копии для отката.

Используются [параметры systemd-resolved](https://www.freedesktop.org/software/systemd/man/latest/resolved.conf.html) и [Unbound](https://unbound.docs.nlnetlabs.nl/en/latest/manpages/unbound.conf.html). Docker daemon DNS не переписывается. Это host resolver: DNS контейнеров с отдельной network namespace требует отдельной проверки. Нода/Caddy используют host network.

## Мониторинг и сертификаты

Мониторинг предлагается по умолчанию. Systemd timer каждые пять минут проверяет контейнеры, совпадение работающего ядра с установленным форком, свободное место под Docker (порог 10%) и TLS-сертификат selfsteal (предупреждение за 14 дней).

При установке проверяются Caddyfile и постоянный volume /data для ACME-сертификатов. Продлением занимается Caddy. Проверка хранилища и текущего сертификата не имитирует будущее продление: DNS и TCP 80 должны оставаться доступны.

Можно указать HTTPS webhook. URL хранится в root-only /etc/remna-bootstrap/monitor.json. Отправляется JSON с полями node, status, problems; для Telegram/Slack нужен принимающий шлюз под этот формат. API-токен панели мониторингу не нужен. Без webhook события доступны в журнале:

```bash
systemctl status remna-monitor.timer
journalctl -u remna-monitor.service
```

Первый здоровый запуск и повторное неизменное состояние проходят молча. При первой ошибке, изменении проблем и восстановлении появляется событие. Неудачная доставка повторяется при следующем запуске. Монитор не проверяет полноценный VLESS и не запрашивает статус панели.

## Внешний тест VLESS / Reality / Vision

В конце можно создать изолированный тестовый Squad с одним новым inbound и пользователя на один час с лимитом 100 МиБ. Доступа к другим inbound’ам рабочей группы нет. Создаётся root-only /var/lib/remna-bootstrap/external-test.json с SOCKS на 127.0.0.1:10808 и outbound xtls-rprx-vision.

Создать тест позже без повторной настройки:

```bash
sudo bash /root/remnawave-vps-bootstrap/bootstrap.sh --test-user
```

Скопируйте конфиг и external-test.sh на **другую Linux-машину** с современным Xray и curl. Конфиг содержит тестовые credentials: передавайте его по защищённому каналу.

```bash
bash external-test.sh external-test.json
```

Клиент делает HTTPS-запрос к example.com через SOCKS с удалённым DNS и завершает созданный процесс. Можно указать второй аргумент — собственный доступный HTTPS URL. Порт 10808 должен быть свободен. Успешный запрос проверяет путь VLESS/Reality/Vision, но не измеряет производительность или устойчивость к блокировкам.

После проверки на VPS:

```bash
sudo bash /root/remnawave-vps-bootstrap/bootstrap.sh --cleanup-test
```

Удаляются пользователь, тестовый Squad и локальный конфиг. Если в Squad добавили посторонних пользователей, очистка откажется удалять группу. Через час доступ истекает, но запись/группа без команды очистки автоматически не удаляются.

## Локальные проверки

```bash
bash -n bootstrap.sh
bash -n host_options.sh
bash -n rollback.sh
bash -n external-test.sh
python3 -B test_panel_setup.py
python3 -B test_panel_transport.py
```

Тесты используют временные файлы и имитацию API/Docker/systemd. Проверяются повторный запуск без дубликатов/смены ключей, конфликты, добавление inbound без потери существующих, ограниченный пользователь/конфиг Vision, откат с сохранением посторонних изменений, обязательный checksum, восстановление файлов и отказ при повреждении, сохранение digest и отсутствие повторных событий мониторинга.

Стартовый HTML создаётся только при отсутствии index.html; замените его собственным сайтом. После upgrade может требоваться перезагрузка: скрипт сообщает об этом, но не перезагружает VPS автоматически.

API сверялся с [исходниками Remnawave backend](https://github.com/remnawave/backend/tree/main/libs/contract/commands) на 01.10.2026. Отличия вашей версии панели не игнорируются: установка останавливается на API-ошибке.
